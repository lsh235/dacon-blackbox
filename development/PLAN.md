# 블랙박스 영상 분석 AI 대회 개발 계획

- 작성일: 2026-08-26
- 상태: 초기 실행 계획
- 개발 위치: `development/`
- 참고 자료: `../DOC/` (읽기 전용)
- 작업 현황: [`TASKS.md`](./TASKS.md)

## 1. 목표

하나의 `submit.zip`으로 다음 세 가지 결과를 생성하는 재현 가능한 학습·추론 파이프라인을 만든다.

1. Stage 1: 원본 영상과 재녹화 영상 분류
2. Stage 2: 충돌 프레임, 진입 프레임, 회피 공간 여부, 진입 방향 예측
3. Stage 3: 0.1초 단위 가감속 및 조향 범주 예측

최종 결과물은 평가 서버에서 인터넷 연결 없이 실행되고, 대회가 요구하는 함수·파일 구조·자원 제한을 만족해야 한다. 2차 평가에 대비하여 모델 개발 과정과 학습데이터 구성 근거도 실험 단계부터 기록한다.

## 2. 현재 확인된 제출 계약

### 필수 추론 함수

`inference.py`는 모듈 최상위에 아래 함수를 제공해야 한다.

```python
predict_stage1(data_dir, model_dir)
predict_stage2(data_dir, model_dir)
predict_stage3(data_dir, model_dir)
```

각 함수는 다음 컬럼을 가진 `pandas.DataFrame`을 반환한다.

| Stage | 필수 컬럼 |
| --- | --- |
| Stage 1 | `ID`, `answer` |
| Stage 2 | `ID`, `collision_frame`, `entry_frame`, `evasion_space`, `entry_side` |
| Stage 3 | `ID`, `sample_index`, `accel_label`, `steer_label` |

Stage 2는 평가 입력 이미지 파일명에 포함된 원본 프레임 번호를 그대로 반환해야 한다. Stage 3의 `sample_index`는 0.1초 단위 순번이다.

### 제출 ZIP 구조

```text
submit.zip
├── inference.py
├── requirements.txt
└── model/
    ├── stage1/best.pt
    ├── stage2/best.pt
    ├── stage2/resnet18-f37072fd.pth
    └── stage3/best.pt
```

모델 구성이 바뀌면 `model/` 내부 파일은 변경할 수 있지만, `inference.py`가 모든 파일을 상대 경로로 찾고 평가 서버에서 외부 다운로드 없이 로드할 수 있어야 한다.

### 평가 서버 제약

| 항목 | 제한 |
| --- | --- |
| 전체 추론 | 60분 이내 |
| 패키지 설치 | 10분 이내 |
| 제출 ZIP | 10GB 이내 |
| 압축 해제 후 | 32GB 이내 |
| 인터넷 | 비활성화 |
| GPU | NVIDIA L40S, VRAM 44.7GiB |
| CPU / RAM | 7 vCPU / 60GB |
| 공유 메모리 | 30GB |

## 3. 확인이 필요한 선행 항목

아래 항목은 현재 `DOC/`만으로 확정할 수 없으므로 임의로 가정하지 않는다.

- 공식 Stage별 평가 지표와 Stage 통합 점수 계산 방식
- 실제 전체 학습데이터의 제공 범위, 경로 구조 및 라이선스
- 외부 데이터, 사전학습 가중치, 합성 데이터 사용 허용 범위
- Stage 2의 `evasion_space` 값 정의와 결측·판정 불가 값 처리 규칙
- 평가 영상의 FPS와 Stage 3의 정확한 10Hz 샘플 매핑 규칙
- 추가 제출 파일 허용 여부와 `requirements.txt` 패키지 설치 방식

현재 `DOC/Overview/Evaluation.yaml`은 비어 있다. 공식 공지나 평가 문서가 확보되면 요구사항 표와 로컬 평가기를 먼저 갱신한 뒤 모델 비교를 시작한다.

## 4. 공개 예제의 한계

- 공개 예제는 Stage별 소규모 실행 확인 자료이므로 일반화 성능을 판단하는 학습 세트로 사용하지 않는다.
- Stage 1의 재녹화 예제는 실제 기기로 재촬영한 데이터가 아니라 특성을 모사한 파생 예제다.
- Stage 2 예제는 충돌 시점 라벨만 제공한다. 진입 시점, 회피 공간, 진입 방향 출력은 실행 구조 확인용이며 학습 성능의 근거가 아니다.
- Stage 3 예제는 희소 라벨이므로 실제 성능 확보를 위해 별도 데이터 구성과 라벨링 전략이 필요하다.

따라서 공개 예제로는 입출력 계약, 오류 처리, 모델 로딩, ZIP 구성과 스모크 실행만 검증한다.

## 5. 개발 디렉터리 구조

```text
development/
├── PLAN.md                 # 이 실행 계획
├── configs/                # 공통 및 Stage별 실험 설정
├── data/
│   ├── raw/                # 원본 학습데이터 또는 외부 경로 링크
│   ├── interim/            # 프레임, 특징 등 중간 산출물
│   ├── processed/          # 학습 직전 데이터
│   ├── splits/             # 재현 가능한 train/valid 분할
│   └── metadata/           # 출처, 라이선스, 라벨 버전, 해시
├── notebooks/              # 탐색과 시각화 전용 노트북
├── stages/                 # Stage별 문제 이해·조사·실험 문서
│   ├── stage1/
│   ├── stage2/
│   └── stage3/
├── src/blackbox/
│   ├── common/             # 영상 I/O, 설정, 시드, 공통 유틸리티
│   └── stages/
│       ├── stage1/         # Stage 1 모델·학습·추론
│       ├── stage2/         # Stage 2 모델·학습·추론
│       └── stage3/         # Stage 3 모델·학습·추론
├── scripts/
│   ├── data/               # 데이터 검사와 전처리 진입점
│   ├── train/              # Stage별 학습 진입점
│   ├── evaluate/           # 로컬 평가와 오류 분석
│   └── submission/         # inference.py 생성과 ZIP 검증
├── tests/
│   ├── unit/               # 변환, 샘플링, 스키마 단위 테스트
│   ├── integration/        # Stage별 및 전체 추론 테스트
│   └── fixtures/           # 작고 재배포 가능한 테스트 픽스처
├── artifacts/
│   ├── checkpoints/        # 학습 가중치
│   ├── features/           # 특징 캐시
│   ├── predictions/        # 검증 예측
│   ├── logs/               # 실행 로그와 프로파일링 결과
│   └── submissions/        # 제출 후보 ZIP
└── reports/
    ├── experiments/        # 실험별 가설·설정·결과
    ├── figures/            # 오류 분석 및 보고서 그림
    └── submission/         # 모델·학습데이터 구성 보고서 초안
```

대용량 데이터와 생성 산출물은 Git에 포함하지 않는다. 노트북에서 검증된 로직은 `src/` 또는 `scripts/`로 옮기고, 제출 코드는 노트북 셀에만 존재하지 않게 한다.

### Ubuntu 24.04 개발 환경

시스템 Python을 직접 변경하지 않고 프로젝트 전용 `.venv`를 사용한다.

```bash
cd development
make setup
make check
```

`make setup`은 Ubuntu 24.04에 `ensurepip`이 없는 경우에도 가상환경 내부에 pip를 복구한 뒤 `requirements.txt`의 정확한 버전을 설치한다. `make check`는 환경 버전과 CUDA를 먼저 검사하고 Python 컴파일, 단위 테스트와 제출 계약 스모크를 순서대로 실행한다.

## 6. 단계별 실행 계획

### M0. 요구사항 고정

작업:

- `DOC/Overview`, `DOC/Data`, `DOC/Code`의 요구사항을 항목별 체크리스트로 변환한다.
- 누락된 평가 지표와 데이터·외부 자료 사용 규칙을 공식 자료로 확인한다.
- Stage별 입력 경로, 출력 타입, 허용 값과 예외 상황을 테스트 계약으로 정의한다.
- Python, CUDA, PyTorch, torchvision, OpenCV 버전을 평가 환경과 맞춘다.

완료 조건:

- 모델 선택에 영향을 주는 미확정 규칙이 없거나 명시적인 보류 항목으로 기록되어 있다.
- 필수 함수와 출력 스키마를 검사하는 테스트 명세가 작성되어 있다.

### M1. 베이스라인 재현 및 실행 기반 구축

작업:

- `DOC/Code`의 학습·추론 흐름을 `development/` 코드로 분리해 재현한다.
- 시드, 설정 파일, 실행 로그, 체크포인트 메타데이터를 공통화한다.
- 공개 예제를 `development/data/`로 복사하거나 읽기 전용 원본에서 안전하게 복제하는 준비 스크립트를 만든다.
- 세 Stage의 필수 함수를 한 프로세스에서 순차 호출하는 스모크 테스트를 만든다.
- 실패한 영상 디코딩, 빈 입력, 손상된 체크포인트를 명확한 오류로 처리한다.

완료 조건:

- `DOC/`를 수정하거나 런타임 경로로 의존하지 않고 베이스라인을 실행할 수 있다.
- 세 함수가 정확한 컬럼 순서와 허용 값을 반환한다.
- 동일 설정과 시드로 학습·추론 결과를 재현할 수 있다.

### M2. 데이터·평가 기반 구축

작업:

- 영상 출처, 촬영 장치, 사고 유형 단위로 누수가 없는 그룹 분할을 설계한다.
- 파일 존재 여부, 영상 디코딩, FPS, 프레임 수, 레이블 범위를 자동 검사한다.
- 공식 지표가 확인되면 Stage별 지표와 최종 점수 계산을 그대로 구현한다.
- 데이터 버전, 라벨 버전, 분할 파일과 해시를 실험 기록에 연결한다.
- 외부·합성·자체 라벨 데이터는 출처, 사용 허가와 생성 절차를 기록한다.

완료 조건:

- 모든 실험이 동일한 검증 분할과 공식 지표로 비교 가능하다.
- 중복 영상과 파생 영상이 train/valid 사이에 섞이지 않는다.

### M3. Stage 1 개선

학습·조사 가이드: [`stages/stage1/STUDY_AND_IMPROVEMENT_GUIDE.md`](./stages/stage1/STUDY_AND_IMPROVEMENT_GUIDE.md)

기준선: MViTv2-S, 16프레임 3구간 추론, 클립별 재녹화 확률 평균.

실험 후보:

- 시간 구간 수와 프레임 샘플링 방식 비교
- 해상도·화면 경계·모아레·압축 흔적을 보존하는 증강
- 촬영 장치와 원본 영상 단위 그룹 검증
- 클립별 확률 집계, 임계값 보정 및 경량 앙상블

완료 조건:

- 실제 재녹화 검증 데이터에서 기준선보다 공식 지표가 개선된다.
- 디코딩 실패 시의 정책이 보수적으로 정의되어 있다.

### M4. Stage 2 개선

기준선: ResNet18 프레임 특징과 BiGRU 기반 시점 탐지·장면 분류.

우선 작업:

- 충돌, 진입, 회피 공간, 진입 방향 네 과업의 라벨을 확보하거나 작성한다.
- 원본 프레임 번호와 추출 이미지 파일명의 대응을 보존한다.
- 긴 영상의 특징 추출을 캐시하고, 특징 캐시가 학습·추론 전처리와 동일한지 검사한다.

실험 후보:

- 프레임 단위 시점 점수와 구간 기반 시점 회귀 비교
- 양방향 GRU, Temporal Transformer 등 시간 모델 비교
- 진입 시점과 충돌 시점의 순서 제약을 활용한 후처리
- 회피 공간·진입 방향의 클래스 불균형 보정과 멀티태스크 손실 조정

완료 조건:

- 네 과업 모두 실제 정답이 있는 검증 세트로 평가된다.
- 반환 프레임이 입력 파일명에 존재하며 시간적 제약을 위반하지 않는다.

### M5. Stage 3 개선

기준선: MViTv2-S 공유 백본과 가감속·조향 분류 헤드.

우선 작업:

- 영상 FPS를 정규화하고 평가 기준의 0.1초 표본과 원본 프레임을 정확히 대응시킨다.
- 가감속 4개 범주와 조향 3개 범주의 분포·전이·결측을 분석한다.

실험 후보:

- 단일 클립 모델과 특징 기반 시간 모델 비교
- 클래스 가중치, 균형 샘플링, focal loss 비교
- 차량 거동의 연속성을 활용한 시간적 평활화
- 가감속과 조향의 공동 학습 대비 독립 헤드·모델 비교

완료 조건:

- 모든 영상에서 누락이나 중복 없이 요구된 0.1초 단위 행을 반환한다.
- 후처리가 짧은 실제 거동을 과도하게 제거하지 않는지 오류 분석으로 확인한다.

### M6. 통합 추론 및 성능 최적화

작업:

- 세 Stage 모델을 순차 실행하면서 GPU·CPU 메모리를 명시적으로 해제한다.
- mixed precision, 배치 크기, worker 수, 프레임 디코딩 병목을 프로파일링한다.
- 평가 데이터 규모를 기준으로 최악 조건의 실행시간과 최대 메모리를 추정한다.
- 인터넷·사용자 캐시·절대 경로 없이 새 환경에서 실행한다.
- 학습 전처리와 추론 전처리의 수치 동등성을 테스트한다.

완료 조건:

- 추론 60분, 설치 10분, VRAM 44.7GiB와 RAM 60GB 제한 안에서 안전 여유를 확보한다.
- 각 Stage를 단독 실행한 결과와 통합 실행 결과가 일치한다.

### M7. 제출 후보 생성 및 검증

작업:

- `inference.py`, `requirements.txt`, 모델 파일만 포함하는 ZIP 생성기를 만든다.
- ZIP 경로 순회, 누락 파일, 문법, 필수 함수, 모델 로딩을 자동 검사한다.
- 제출 ZIP 10GB 및 압축 해제 32GB 제한을 검사한다.
- 깨끗한 임시 디렉터리에서 ZIP을 해제하고 공개 예제 전체를 오프라인 실행한다.
- 제출 후보마다 설정, 모델 해시, Git 커밋, 검증 결과를 기록한다.

완료 조건:

- 한 명령으로 제출 후보를 만들고 동일한 검증 결과를 재현할 수 있다.
- ZIP 안에 학습데이터, 캐시, 로그, 노트북과 불필요한 가중치가 없다.

### M8. 2차 평가 문서 준비

작업:

- 실험 가설, 변경점, 지표, 실패 사례와 선택 근거를 계속 기록한다.
- 학습데이터별 출처, 수량, 라이선스, 전처리, 라벨링, 분할 방식을 표로 관리한다.
- 최종 모델 구조, 학습 설정, 추론 후처리, 자원 사용량과 재현 명령을 정리한다.

완료 조건:

- `모델 개발 보고서`와 `학습데이터 구성 보고서`를 실험 기록으로부터 작성할 수 있다.
- 보고서의 모든 성능 주장을 체크포인트와 평가 결과로 추적할 수 있다.

## 7. 공통 검증 게이트

모든 Stage와 제출 후보는 아래 검증을 통과해야 한다.

1. 데이터 게이트: 파일, 프레임, FPS, 레이블 값, 중복·누수 검사
2. 코드 게이트: 단위 테스트, 타입·스키마 검사, 결정적 시드 설정
3. 성능 게이트: 동일 분할·동일 공식 지표에서 기준선과 비교
4. 통합 게이트: 필수 함수 세 개를 실제 입력 구조로 순차 실행
5. 자원 게이트: 시간, VRAM, RAM, worker 수와 디스크 사용량 기록
6. 제출 게이트: 오프라인 새 환경에서 설치, 압축 해제, 추론까지 검증

공식 평가 지표가 확인되기 전에는 정확도 목표치를 임의로 정하지 않는다. 그 전까지의 결과는 파이프라인 검증과 오류 분석 결과로만 기록한다.

## 8. 실험 기록 형식

모든 실험은 최소한 다음 정보를 `reports/experiments/`에 남긴다.

- 실험 ID와 목적
- 코드 커밋과 설정 파일
- 데이터·라벨·분할 버전
- 모델 초기값 또는 사전학습 가중치 출처
- 학습 환경, 실행 명령, 시드와 소요 시간
- Stage별 공식 지표와 기준선 대비 변화
- 실패 사례, 해석, 다음 결정
- 생성된 체크포인트와 예측 파일의 해시

## 9. 최종 완료 정의

- 세 Stage의 학습과 평가를 독립적으로 재현할 수 있다.
- `inference.py`의 세 필수 함수가 정확한 스키마를 반환한다.
- 통합 추론이 오프라인 평가 환경의 시간·메모리 제한을 만족한다.
- 검증된 모델과 코드만 포함한 `submit.zip`이 자동 생성된다.
- 데이터 구성과 모델 선택 근거가 2차 평가 보고서 수준으로 추적된다.
- 개발 과정에서 `DOC/`의 어떤 파일도 변경되지 않는다.
